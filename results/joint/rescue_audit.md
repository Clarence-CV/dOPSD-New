# Joint MATH v1：同状态续写到底救回多少监督

核查日期：2026-10-18 UTC。结论：同状态续写确实找回了相当一部分可训练参考，但代价很大，现有证据不支持把它作为方法必需环节。建议简化主线为：从题目开头最多尝试 8 条 Student 轨迹，找到第一条答案验证通过的轨迹后，均匀抽一个合格状态，用这条轨迹自己的最终组内 token 做 LOO；不再从每个状态额外续写 8 次。该建议尚未训练验证，不能承诺保持原结果。

## 2. “救回”的明确口径

自然轨迹最终答案错误；从其中一个保存状态重新采样，至少一条续写答案通过验证，并且该续写在组 G 上的整体 token tuple 通过冻结 Teacher 的全部 LOO 检查。只有最后这一步通过，状态才进入训练 loss。

这表示**找回可用监督**。它不等于训练后的 Student 学会了纠正这些题，也不能说明取出的中间状态已经包含错误：自然轨迹的错误可能发生在取样点之后。此前自然轨迹由训练中的 Student 生成，不是把固定 base 做错的题作为独立集合。

| 指标 | 自然轨迹原本答错 | 自然轨迹原本答对 |
| --- | ---: | ---: |
| 题目 / 自然轨迹 | 226 | 101 |
| 至少一个抽样状态找到答对续写的题目 | 88 / 226 = 38.9% | 101 / 101 = 100% |
| 至少一个抽样状态通过 LOO、进入 loss 的题目 | **77 / 226 = 34.1%** | 101 / 101 = 100% |
| 抽取状态数 | 904 | 404 |
| 有答对续写的状态 | 189 / 904 = 20.9% | 398 / 404 = 98.5% |
| 通过 LOO 的状态 | **154 / 904 = 17.0%** | 371 / 404 = 91.8% |
| 受监督 token 位置 | **593** | 1,426 |
| 续写条数 | 7,232 | 3,232 |
| 续写 NFE（前向次数） | **371,419** | 132,070 |

77 条的统计使用了 **4 个状态 × 每状态 8 条 = 每题 32 条额外续写**。不能将它写成“单状态 pass@8 救回 34.1%”。这些采样是条件续写，不是 32 条从 prompt 独立出发的完整轨迹。

若只从已经保存的每题 4 个状态中均匀选一个，保留该状态原有的 8 条候选，错轨迹中贡献监督的题数期望为 `154 / 4 = 38.5`，即 17.0%。这是对现存候选库的子采样计算；重新训练后 Student、轨迹与状态分布都会变化，不能作为新方法的效果预测。

## 3. 收益与成本

- 错轨迹来源贡献了 29.3% 的有效状态（154/525）和 **29.4% 的监督位置（593/2019）**。
- 它们消耗 **73.8% 的全部续写 NFE**。获得一个有效状态平均需要 2,411.8 次续写前向；原本答对轨迹来源为 356.0 次，相差 **6.78 倍**。
- 错轨迹来源的续写 NFE 中，80.4% 花在最终没有通过认证的状态上。
- 所有自然轨迹共 31,934 NFE；额外续写共 503,489 NFE，约为自然轨迹的 **15.77 倍**。这体现了当前采样开销，不是替代方案实测加速比。
- NFE 是已记录的前向调用次数，不是 GPU 秒或 SU；未包括 group readout、Student 训练/反向及其他开销，也没有对不同长度、forward 路径作时间加权。

因此不能说这部分“毫无用处”：29.4% 的监督来自它。也不能据此说它“必需”：没有删去该分支的训练消融，也没有同等计算预算下的 prompt 重采样对照。

现有整个 Joint 模型在原 MATH-500 评分口径上，base 172/500 → Joint 175/500；32 题错→对、29 题对→错，净增 3 题，配对 p≈0.80。实际时延减少约 11%，步数减少约 18%。这些属于**完整方法**的结果，不能归因于救回的 77 条训练轨迹。

## 4. 自己的成功轨迹能不能直接当参考

可以。对已提交 token 不再改写的解码，成功轨迹 Y 的任一先前状态 S，与 Y 的最终 token 天然相容。取 `pi = Y[G]`，即可直接调用与原来相同的 LOO；Teacher 无需知道 pi 是来自原轨迹还是额外续写。实现仍应检查已提交 token 相容性，避免迁移到会改写 token 的解码器时误用这个性质。

还能用保存的 LOO 记录验证一部分结果：当自然成功轨迹的组内 tuple 与某条已检测候选的 tuple 完全相同，输入给冻结 Teacher 的状态、可见 token、预测位置也完全相同，其已保存结果可直接复用。

| 原本答对轨迹的 404 个抽样状态 | 数量 | 占比 |
| --- | ---: | ---: |
| 自身最终 tuple 已在记录中通过 LOO | **287** | **71.0%** |
| 自身最终 tuple 已在记录中被 LOO 拒绝 | 40 | 9.9% |
| 自身最终 tuple 没被检测，结果未知 | 77 | 19.1% |

所以，**至少 287 个状态不需要另找续写就已有可认证参考**。不能将其余 77 个未知状态记为失败；这里没有做新 Teacher 推理。原先同状态续写方案在这批成功来源状态上接受 371 个状态，直接自身 tuple 的可接受数目前仅知介于 287 与 364 之间。原本自身 tuple 明确失败的 40 个状态中，有 18 个被替代 tuple 成功救回，说明多候选确实也能解决局部 LOO 不一致，但仍不证明值得默认支付其成本。

## 5. 建议采用的最简训练采样协议

```text
从训练集取一题
  → 当前 Student 从 prompt 生成完整轨迹，并保留去噪状态
  → 验证最终答案；失败则从 prompt 重试，总尝试上限 8
  → 得到第一条成功轨迹；8 次均失败则跳过本题
  → 在这条轨迹的合格状态中均匀抽 1 个；没有合格状态则跳过
  → 用该成功轨迹的最终 token 在 G 上组成唯一参考 pi
  → 检查已提交 token 相容性；对 pi 做逐位置 LOO
  → 全组通过才构造 Teacher 分布和 KL loss；不通过就跳过
```

- 完整生成在这里有清楚用途：验证最终答案，并同时得到相容参考。回看保存状态只需读内存，不会再把前缀跑一遍。均匀抽一个状态不需要再设置偏好的去噪时刻，也避免每题重复利用大量相关状态；这是简约采样单位，不是“一个状态在统计上最优”的定理。
- 组 G 的定义继续与最终解码的 confidence 协议对齐；不能为了采样方便另设固定组大小。mini 的具体实现仍须先完成官方解码复现。
- 保留现有 LOO 语义：预测 i 时，只揭开 G 中其他参考 token，i 仍为 MASK，其他位置保持 S；要求每个位置 Teacher argmax 等于 pi_i。它认证局部一致性，数学答案正确性来自独立的终局验证。
- Student 输入仍是 S 和自己的 draft soft message，不能输入 pi 或成功轨迹尾部。PI 只进入 Teacher 目标。
- 取消同状态 K8 候选库后，也可以取消 embedding-distance 排序和在多个 tuple 中逐个搜索的分支。这不改变 LOO 判据或训练注入结构，但会改变参考分布，必须重新验证效果。
- 每题从 prompt 的预算上限 8 是可审计的资源预算，沿用已有 OPSD 对照；不是理论要求，也不是报告 task pass@8。训练重采样必须有随机性，不能把同一个确定性 greedy 结果重跑八遍。训练采样与官方 greedy 评测的温度分别记录。
- 数据应准确称为 **Student 生成、经成功筛选的状态**。它仍有成功筛选偏差，不能宣称覆盖无条件 Student 状态分布；失败轨迹仍保存用于诊断，主线不为其额外分支搜索。
- 如后续要声称“从失败轨迹找回监督”是创新/必要贡献，才需要专门的同等训练计算预算对照，报告 held-out accuracy、实际 latency、获得参考数量和成本；当前不增加该实验分支。

这一协议的外部依据与本项目设计要分开：

1. **从 prompt 重采样、成功即停止、最多 8 次**：THU d-OPSD 作者代码中 `iter_num = 1` 后的重采样循环明确把原始 `batch_prompt_ids` 再传给 `generate`，默认 `passk: 8`。支持的是这一采样结构，不代表认可其所有解码参数，也不代表它证明了本项目的 LOO 方法。
   - [作者 trainer 固定版本](https://github.com/xingzhejun/d-opsd-code/blob/70d146c525c79c4c6d056bcd69853f1365ce5d8c/d-opsd/d_opsd_trainer.py)
   - [作者配置：passk=8、passk_temperature=0.9](https://github.com/xingzhejun/d-opsd-code/blob/70d146c525c79c4c6d056bcd69853f1365ce5d8c/d-opsd/opsd.yaml)
2. **使用 Student 自产状态做蒸馏**：GKD（ICLR 2024）支持这一一般方向；它不证明本项目成功筛选无偏，不要求每个状态 8 次续写，也不规定每条轨迹抽 4 个状态。
   - [GKD 作者论文](https://arxiv.org/abs/2306.13649)
3. **成功轨迹自身 token + 单状态 + LOO**：是本项目依据相容性、已有认证记录和成本作出的简化方案。不能冒称是官方 mini 或已有顶会论文的完整既定配方。它保留了需要研究的 sibling-conditioned Teacher 目标，减少了额外候选搜索带来的解释负担。

没有方案能保证审稿人不提出问题。当前更可辩护的做法是：主线结构简单、成功筛选口径诚实、额外搜索不冒充必需机制，最终效果由独立验证集和测试集回答。

## 6. 附：只看候选答案成功率时，8 次的边际收益

按每份已保存候选库的实际顺序，查看前 K 条中是否有正确答案；这不是减小 K 后重新运行 LOO 的结果。

| 前 K 条候选 | 错轨迹来源状态：至少一条答对 / 904 | 对轨迹来源状态：至少一条答对 / 404 |
| --- | ---: | ---: |
| 1 | 66 = 7.3% | 358 = 88.6% |
| 2 | 101 = 11.2% | 375 = 92.8% |
| 4 | 143 = 15.8% | 390 = 96.5% |
| 8 | 189 = 20.9% | 398 = 98.5% |

不能从此表推导 prompt 重试 K8 的成功率：初始条件不同；也不能把“存在正确答案”当作“LOO 通过”。较小候选库可能改变 tuple 排序，而原运行只保存到第一个通过者为止的认证，不能完整反推每个 K 的 LOO 接受率。
